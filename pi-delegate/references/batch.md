# Delegating a batch of tickets

Use this when a spec or Wayfinder map has been split into several tickets that should land together
as one PR (ha-spark #394: ten tickets; #409 B1: six). Each ticket is delegated as in SKILL.md; this
file covers what changes when there are many: one shared brief, an integration branch, running
tickets in dependency order, carrying lessons forward, and reviewing the whole batch before the PR.

## Layout

```
<worktree-dir>/                    e.g. ~/ha-spark-wt/
  <spec>/                          integration worktree, branch feat/<spec>-<slug>
  <spec>-<N>/                      one ticket worktree per ticket, branch <spec>-<N>
  <spec>-<N>.pi.jsonl / .err / .start   run logs (run.sh writes these)
  <spec>-notes/
    preamble.md                    shared brief, from assets/batch-preamble.md
    spec.md                        the spec issue, verbatim
    ticket-<N>.md                  each ticket issue, verbatim
    notes-<N>.md                   your evidence and pointers for ticket N
    carry-forward.md               lessons from reviews that later tickets need
    brief-<N>.md                   generated by scripts/brief.sh
```

## 1. Set up once

1. Read the spec and every ticket from the source of truth: the Wayfinder map or the spec's GitHub
   issues, with their "Blocked by" links. Work out the dependency order and group it into waves,
   with a model for each ticket. Show the user the waves once, before the first launch; that is the
   only up-front confirmation.
2. Create the integration branch and its worktree off the default branch:
   `git -C <repo> worktree add -b feat/<spec>-<slug> <worktree-dir>/<spec> origin/<default-branch>`.
3. Write `preamble.md` from [../assets/batch-preamble.md](../assets/batch-preamble.md). Put everything
   true for every ticket here once: conventions, method, gates, and the full **Never change** list.
   That list is what stops a delegate relaxing a guard; it is the most important part of the batch.
4. Save `spec.md` and each `ticket-<N>.md` verbatim (the jail can't fetch issues).

## 2. Run tickets in waves

A ticket is ready when every ticket it depends on is merged into the integration branch. Run all
ready tickets in parallel, one worktree each, cut from the integration branch's current tip:

```sh
git -C <repo> worktree add -b <spec>-<N> <worktree-dir>/<spec>-<N> feat/<spec>-<slug>
scripts/brief.sh <notes-dir> <N> > <notes-dir>/brief-<N>.md
scripts/run.sh <worktree-dir>/<spec>-<N> <model> <notes-dir>/brief-<N>.md
```

Before writing each brief, write `notes-<N>.md`: what is already merged on its base and the names
it introduced (functions, fields, files), the exact places the ticket touches with line numbers,
evidence the jail can't fetch, and any line from `carry-forward.md` that applies. In #394 these
notes carried most of each brief's ticket-specific value; the preamble alone is too general.

Fit each wave to the Go window (SKILL.md, "The Go allowance"): `scripts/bench.sh --window` plus
the estimate for the runs you're launching must stay under 15%. Large tickets go to gpt-6.1-sol on
Plus by default; spread the rest across Go models so one model's spend doesn't dominate. Plus runs
have no cap. A wave may carry one trial run (SKILL.md, "Trying new models") on a ticket that touches
no Never-change item.

Once the waves are confirmed, run the batch end to end without asking between waves; send the
user a one-line update as each wave lands. Stop and ask only for:
- a product decision a delegate raised, or one you can't make from the spec;
- a 429, or a wave that can't fit the window and has no Plus fallback;
- a ticket that has failed review twice.

## 3. Review and merge each ticket

Review each ticket as in SKILL.md step 4: gates, whole diff, every Never-change item that the
ticket goes near, scope. When the ticket touches a Never-change item or is large, also run a
delegated read-only review ([../assets/review-brief-template.md](../assets/review-brief-template.md))
on a different model from the one that wrote it, and verify its findings. Then:

- **Passes:** record the outcome (SKILL.md, "Benchmark"), commit in the ticket worktree (`<type>(<area>): <summary> (#<N>)`), then merge into
  the integration branch from its worktree: `git merge --no-ff <spec>-<N> -m "Merge #<N> into
  <batch>"`. Run the gates on the integration worktree after each merge; a ticket that passes alone
  can still conflict in behaviour with its neighbours.
- **Blocked or short:** if the delegate stopped on a real question, decide it (or ask the user if
  it is a product decision), then rerun in the same worktree with the partial work kept: write the
  ruling to a file headed `## CONTINUATION: <what changed>`, and build the brief with
  `scripts/brief.sh <notes-dir> <N> <continuation-file>`. Log it under a new name (`<spec>-<N>b`)
  so the first attempt's log survives. Small gaps are cheaper to fix yourself.
- **Learned something later tickets need** (a naming decision, a gotcha, a constraint the spec
  didn't state): add one line to `carry-forward.md`, prefixed with the ticket it applies to, and
  copy it into that ticket's notes when you write them.

If a ticket ran on a base that has since moved, merge the integration branch into it before
reviewing, so you review it against what it will land on.

## 4. Review the whole batch

When every ticket is merged, review `git diff <default-branch>...feat/<spec>-<slug>` as one change.
Tickets reviewed one at a time miss what only shows when they combine. Run two read-only reviews in
parallel from [../assets/review-brief-template.md](../assets/review-brief-template.md), on models
that did not write most of the batch, with the safety review on a Plus model (see SKILL.md "Roster"):

- **Spec:** does the batch meet every acceptance criterion of every ticket and the spec?
- **Safety and standards:** every Never-change item, line by line against the default branch, plus
  the repo's conventions.

Verify each finding, fix the real ones on the integration branch (`fix(<area>): address #<spec>
review findings`), and rerun the gates.

## 5. Land and clean up

Open one PR from the integration branch with a `Closes #<N>` line for every ticket and the spec,
unless the user said "hold the PR". Report per ticket: model, cost (`scripts/cost.sh`), number of
runs, what the reviews found and how it was fixed; then the batch totals. Restore any protect list
you lifted. After merge, remove every `<spec>*` worktree and branch; keep `<spec>-notes/` and the
logs.
